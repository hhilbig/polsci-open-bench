## Eligibility decisions

The candidate roster is selective rather than exhaustive. Published parameter counts and active-parameter claims do not establish whether a checkpoint can run reliably on Hive. Feasibility depends on the actual weight files, available quantization, supported inference kernels, GPU and host memory, and the GPUs that can be allocated together on one node. Some recent open-weight models therefore remain unevaluated even with access to multi-GPU hardware. Their exclusion records a practical feasibility limit, not an assessment of their benchmark quality.

- **MiniMax M3:** not evaluated. NVIDIA NVFP4 revision `901464083161bf8612a29ff7ad29914cd4ab4a85` loaded far enough to initialize four distributed workers, but the pinned official runtime rejected every clamp-preserving NVFP4 MoE backend on SM120 before loading model layers or generating output. Native BF16 and official MXFP8 weights exceed the viable single-node allocations. The failed attempt is retained; no semantics-changing workaround was used.
- **GLM-5.3-Flash:** not evaluated pending a supported runtime. [Issue 55773](https://github.com/vllm-project/vllm/issues/55773) remains open, with an independent September 16 report of the NoPE sparse-attention cache assertion. The quantized alternative reduces weight memory but does not resolve this runtime failure. No speculative local kernel patches are part of this expansion.
- **GLM-5.3:** not evaluated. Official FP8 exceeds eight A100 GPUs; documented NVFP4 exceeds four Blackwell GPUs. An AWQ alternative can fit the A100 memory budget provisionally, but the [Ampere runtime proposal](https://github.com/vllm-project/vllm/pull/38476) remains unmerged. This is not a claim that all implementations are impossible.
- **Kimi K3:** not evaluated. Its native MXFP4 weight files total 1,560,936,091,448 bytes, beyond the listed single-node GPU capacity before overhead. Multi-node inference is outside the approved scope.
